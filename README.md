# crawler_hub —— 舆论声量监控平台

覆盖小红书、微博、抖音、快手、知乎、B站、黑猫投诉、百家号、头条号、微信公众号共 10 个平台，统一采集帖子的**标题 / 正文 / 链接 / 作者 / 发布时间 / 点赞 / 评论 / 转发 / 收藏 / 阅读**，落 SQLite，做主体 × 情感两维清洗与声量换算，可导出 Excel / JSONL，也可接入大模型出分析报告。

需登录的平台走「一次扫码 → 登录态落盘 → 后续无头静默抓取」。

## 快速开始

```bash
pip install -r requirements.txt
python -m playwright install chromium

python -m hub.cli serve      # ← 推荐：起本地控制台 http://127.0.0.1:8765，页面上点按钮操作
```

控制台左侧分两组、共六页：

**监控分析** — ① 数据看板（KPI + 声量换算 + 按日趋势/累计、日历热力、主体×情感、关键词云、TOP 帖子/作者、平台覆盖与新鲜度）；② 帖子明细（按平台/分层/主体/情感筛选，悬停看逐条判定依据）；③ 分析报告（接入大模型出报告）。

**采集运维** — ④ 采集与任务（原「发起采集」+「任务中心」已合并：关键词、**独立的采集时间范围**、上限、相关性闸门、平台勾选，下面直接跟任务列表和可滚动的完整日志）；⑤ 平台与登录（「扫码登录」弹真实浏览器窗口，「体检」是功能性探测不是猜 cookie）；⑥ 历史与导出（采集历史可一键把参数填回表单重跑、重新分层、导出 Excel / JSONL 到 `data/exports/`）。

服务只监听 `127.0.0.1` 且**没有鉴权**——它能直接驱动你的登录态浏览器，不要绑 `0.0.0.0` 或做端口转发暴露到局域网。`data/llm.json` 里的 api_key 是明文，`data/` 整个目录都不要提交。

纯命令行也行：

```bash
python -m hub.cli platforms                      # 平台与可采指标一览
python -m hub.cli login xhs douyin kuaishou      # 打开浏览器扫码，登录态持久化
python -m hub.cli status --check                 # 真开浏览器体检登录态

python -m hub.cli crawl -k "开屏广告" -k "摇一摇广告" \
    -p weixin,baijiahao,toutiao,weibo -n 60 \
    --since 2026-06-01 --until 2026-08-31

python -m hub.cli export --since 2026-06-01 --xlsx --jsonl
```

`crawl` 常用开关：`--headful`（出验证码时手工过一下）、`--no-login-check`（跳过预检直接试）、`--debug`（打异常栈）。

## 架构

```
hub/config.py       路径 / UA / 视口 / 超时 / 限速
hub/models.py       Post 数据类；万亿单位换算；engagement = 赞 + 评*2 + 转*3 + 藏*2
hub/session.py      登录态中枢：每平台一个持久化 Chrome profile + state JSON
                    interactive_login() 有头扫码轮询；SilentSession 无头复用
hub/intercept.py    XHR 响应拦截（page.on("response") 收 JSON）
hub/store.py        SQLite（posts 主键 platform+post_id，upsert；runs 采集日志）+ 导出
hub/clean.py        复用 kaiping_sentiment 词表抽负面证据 → 折算 layer
hub/tagging.py      主体（政务/官媒/媒体/平台号/大V/自媒体/普通用户）+ 情感 + 相关性闸门
hub/sov.py          声量换算：观测量→平台内归一→缺失插补→log 压缩×主体权重
hub/wordcloud.py    关键词云（n-gram + 停用词 + 长词优先，零依赖）
hub/llm.py          大模型接入（OpenAI 兼容协议）与分析报告生成
hub/platforms/*.py  各平台适配器，@register 注册到 REGISTRY
hub/cli.py          platforms / login / status / crawl / export
hub/server.py       本地控制台后端 + 静态页（hub/web/）
```

两个关键取舍：

1. **不逆向签名**。小红书 `x-s`、抖音 `a_bogus`、快手 GraphQL 签名都在真实页面里由前端算好，我们只在 Playwright 里翻页并拦截返回的 JSON（`hub/intercept.py`），签名换代也不用跟着改。
2. **登录态即资产**。`launch_persistent_context` 每平台一个 profile 目录（`data/profiles/<平台>`），扫码一次之后无头模式直接复用；`data/state/<平台>.json` 记 `logged_in / last_login / last_check`，`status` 命令可复检。

## 平台能力矩阵（本机实测，2026-09-01）

- **微信公众号** `weixin`｜免登录｜标题/正文摘要/永久链接/公众号名/日期｜**无互动数**
  双通道：百度 `site:mp.weixin.qq.com`（带时间区间、拿永久链接）+ 搜狗微信（补广度）。实测 12/12 条。
  阅读数/点赞数**拿不到**：只有三条路——① MITM 代理抓 PC/手机微信客户端流量（wechat_articles_spider / wechat_spider 的做法）；② 公众号后台 cookie+token 读自家文章；③ 付费第三方接口。`attach_mitm_metrics()` 里显式抛 NotImplementedError 并写明这三条路，不做假数据。
- **百家号** `baijiahao`｜免登录｜标题/正文摘要/链接/来源号/日期｜**无互动数（已核实）**
  入口是百度 `site:baijiahao.baidu.com` + `gpc=stf=<起>,<止>|stftype=1` 时间区间。实测 12/12 条。
  文章唯一标识是 URL 里的 `id=` 参数（`baijiahao_id()`），**不能按路径末段取**——那样每篇都得到 `"s"`，入库会互相覆盖（已踩过：12 条塌成 1 条）。
  评论走百度评论中台 `ext.baidu.com/api/comment/v2/comment/list`（JSONP），实测这些文章 `comment_count` 一律为 0（连新华社、光明网稿也是 0），DOM 里也没有赞/评数字——所以互动列是真的空，不是抓漏。
- **头条号** `toutiao`｜免登录｜标题/摘要/链接/作者/精确时间｜**点赞/评论/转发/阅读（网页镜像口径）**
  `so.toutiao.com/search?pd=information` 是服务端渲染，没有搜索 JSON 接口；解析 `div.result-content` 的 `cr-params` 属性取 `gid`+标题，翻页用 `offset=页码*10`。实测 15/15 条。
  互动数由 `_enrich()` 逐条调 `m.toutiao.com/i<gid>/info/`（免登录）补齐：`digg_count / comment_count / repost_count / impression_count` + 精确 `publish_time`。
  **但这是网页镜像侧的口径**，实测普遍个位数到几十（如钱江晚报那篇 impression 122 / 评论 2），不等于 App 内热度，别当 App 数据用。未登录时详情页 `article/v4/tab_comments/` 一直返回 0，`api/pc/info` 是空壳，所以只能走 info 接口。
- **微博** `weibo`｜登录可选（`LOGIN_OPTIONAL`）｜正文/永久链接/精确时间/作者｜**转发/评论/点赞**
  登录后两条路一起用：① `s.weibo.com` 高级搜索 **按天切片**（`timescope=custom:<日>:<日>`，每天翻到 10 页）；② `m.weibo.cn/api/container/getIndex` 的**综合（type=1）+ 实时（type=61）**两个容器各自翻页补量。实测 2026-08-01~08-31、上限 40 条，33 秒拿到 40 条真实数据（8-31 有 16 条、8-30 有 25 条），永久链接形如 `weibo.com/<uid>/<bid>`，可直接打开正文。
  **「微博接口免登录随便爬」现在不成立**：匿名调 `getIndex`，`type=1/61` 都只有 `page=1` 返回数据，`page>=2` 一律 `ok=-100`；带登录态两个容器都能翻到 7 页以上（实测共 141 条）。所以匿名只能拿到十条左右，代码里会把「有效深度 N 页」打进日志，不静默少数据。
  时间和永久链接都在卡片的 `div.from > a` 上（早先按 `p.from` 取，选择器不匹配 → 时间和链接双双为空，已修）。登录态判断**不靠 cookie 猜**——旧 `SUB` cookie 会让 `is_logged_in()` 假阳性、进而走 PC 路径静默返回 0 条，现在改成功能性探测；匿名走接口前必须先真实 `goto` 一次 m.weibo.cn（移动 UA）拿新 `SUB`，否则 `ok=-100`。
- **小红书** `xhs`｜**需登录**｜点赞/评论/收藏/分享
  拦截 `/api/sns/web/v1/search/notes`，映射 `note_card.interact_info`；有 `section.note-item` DOM 兜底。**待扫码验证。**
- **抖音** `douyin`｜**需登录**｜点赞/评论/分享/收藏/播放
  拦截 `/aweme/v1/web/general/search/single/` 等，`statistics` → digg/comment/share/collect/play。未登录实测 0 条：匿名搜索会被 verify center（`rc-verifycenter/rmc-nocaptcha`）拦下，必须先 `login douyin` 扫码。**待扫码验证。**
- **快手** `kuaishou`｜**需登录**｜点赞/评论/分享/播放
  拦截 `/graphql`，`photo` → likeCount/commentCount/shareCount/viewCount。**待扫码验证。**

小结：**10 个平台全部实测跑通**（登录态体检 10/10）。需登录的是小红书 / 微博 / 抖音 / 快手 / 知乎 / 黑猫投诉（黑猫用微博账号），其余免登录。
快手的搜索接口已从 `/graphql` 迁到 `/rest/v/search/feed`，两个都拦以兼容；只拦旧路径会同时表现为「登录态显示未登录」和「每次采集 0 条」。

## 清洗口径：主体 × 情感（两维标注）

原来只有一层 A/B/C/D，"谁在说"和"什么倾向"揉在一起，看不出声量结构。现在每条数据带两个维度，各自附判定依据，可在明细里逐条复核：

- **主体（`actor`，只看账号身份，不看正文）**：`官方机构`（网信办/工信部/市监/消协/公安/政务号）→ `官方媒体`（央媒党媒 + 省级党报）→ `新闻媒体`（持证媒体、地方台、都市报、财经科技媒体）→ `平台企业号`（被投诉的一方，如百度网盘、抖音客服）→ `大V博主`（粉丝 ≥ 5 万，或点赞 ≥ 1000 / 转发 ≥ 300 / 互动 ≥ 3000）→ `自媒体号`（百家号/公众号/头条号里没有媒体特征的账号）→ `普通用户`。
  判定顺序从最确定的证据往下，且**只看作者字段**——正文里的"新华社报道称"不能把发帖人变成官媒。
- **情感（`sentiment`）**：`负面` / `中性` / `正面`。先判负面（舆情场景漏判负面代价最大），再判标题里的明确正面表达，兜底中性。
- `layer` 仍保留（`A_UGC负反馈 / B_媒体负面报道 / C_中性事件报道 / D_噪音 / E_正面反馈`），由主体 × 情感 × 相关性折算而来，看板的口径切换和导出继续用它。

**场景相关性做了本地复核**：共用词表的场景白名单只有开屏/摇一摇等 7 个词，换关键词（如「百度网盘广告」）会把大量真实负反馈误剔成噪音（实测 89% 的噪音都是这个原因）。`hub/clean.py` 里 `scene_rescue()` / `fan_verdict()` / `is_emergency()` 三条通道分别兜「场景说法没覆盖」「饭圈内容要分正负」「应急场景绝不剔噪」，每条救回都会在判定依据里标注「场景复核：…」，可逐条复核。

几条防"乱归因"的规则（都在 `hub/clean.py` 与 `hub/tagging.py` 的注释里）：

- `MEDIA_CRITIC` 里有"整改/违规/调查/实测"这类监管通报天天出现的词，**标题命中才算负面证据，正文要命中两个以上**，否则中性通报会被大面积判成负面。
- `AMBIG_NEG`（直接跳 / 看广告 / 强制 / 被迫…）只在标题里算证据：正文一句"直接跳过引导页"曾把《手机记账软件挑选指南》判成负面。
- 正面词只认标题，且剔掉了"支持/点赞/无广告/清爽"这类泛词——早期版本把"无广告纯净APP推荐"整批判成正面口碑。命中"推荐/测评/哪些/盘点"等横评标记时不给正面。
- 补了三类原词表漏掉的负面表达：激烈口语（我操/我靠/特么/想杀）、取消诉求与质问（能不能取消/真的很难吗/还治不了）、受损场景（跳转广告/塞广告/动都没动）。
- 带情绪的求助（"关闭摇一摇广告真的很难吗？"）不再被"教程类"规则剔成噪音；反过来，软文横评（"无广告APP推荐"）会被单独剔除。

导出的 Excel 多了「主体×情感」交叉表，以及明细里的主体/情感及各自判定依据列。

## 声量怎么算（`hub/sov.py`）

直接把各平台 `engagement` 相加是错的，库里的实测就是理由：微博互动量中位数 40、小红书 48、头条号只有 2（网页镜像口径），而**百家号 221 条 + 微信公众号 177 条的互动数全是 0**——占有效数据 35%。相加的结果是这 35% 内容声量为零，可"人民日报公众号发了一篇批评稿"显然不是零声量。

四步换算，每步都可复算：

1. **取观测量**：微博/小红书/抖音/快手 → `engagement`；头条号 → `views`（它的互动数是镜像口径普遍个位数，阅读数更接近真实到达）；微信公众号/百家号 → 无，进第 3 步。
2. **平台内归一**：`热度 = 观测量 ÷ B_p`，`B_p` 是**从当前这批数据现算的该平台观测量中位数**（不写死系数）。这样"一条普通微博"和"一条普通小红书"都等于 1.0，量级差异被抹平。当前区间实测 `B_p`：小红书 71、微博 57.5、头条号 38。
3. **缺失插补**：无互动数平台按「同主体在有数平台的热度中位数」补，并标 `sov_basis=imputed`。当前实测的主体热度中位数：大V 50.5、官方媒体 2.07、新闻媒体 1.76、普通用户 0.64、自媒体号 0.29。不给 0（等于抹掉声量），也不按均值/最大值补（等于虚高）。
4. **单条声量**：`sov = (1 + log10(1 + 热度)) × 主体权重`
   - `log10` 压长尾：热度 10 倍只算 ~1.6 倍、100 倍算 ~2.4 倍，一条 2.8 万互动的爆款是 4.68 分 ≈ 4.7 条普通内容，不会把整段时间带偏；
   - 常数 `1` 是"内容存在本身"的底分，所以零互动内容仍计 1 分；
   - 主体权重（官方机构 2.0 / 官方媒体 1.8 / 新闻媒体 1.4 / 大V 1.3 / 其余 1.0）补的是**我们抓不到的跨渠道转载放大**，单独乘、单独可调、报表里单独展示——主观部分只集中在这一个旋钮上，不再给平台叠第二层主观系数。

输出三个数而不是一个：**总声量**、**负面声量**（负反馈主口径看这个）、**实测占比**（置信度）。当前区间：有效 910 条 → 总声量 1456 分，负面 890.6 分（61.2%），日均 20.5 分，实测占比 63%。

平台层面换算后的结果（条数 / 声量分 / 人均分）：微博 305/452.7/1.48、小红书 165/282.4/1.71、百家号 199/275.9/1.39、微信公众号 141/250.3/1.78、头条号 100/194.8/1.95 —— 无互动数的两个平台不再是 0，人均分也落在实测平台同一区间，没有虚高。

看板「声量换算」区块给出平台声量（负面/其他分色 + 条数虚线）与按日声量趋势，底部标注实测/估算条数；导出 Excel 多一张「声量测算说明」，把公式、当期基线、主体热度中位数、主体权重全部写进去，便于复核与调参。

## 接入大模型做分析（`hub/llm.py`）

填 `base_url + api_key + 模型名`就能用，走各家都认的 OpenAI 兼容 `/chat/completions`；配置存 `data/llm.json`，**重启后还在**，页面上只回显打码后的 key（保存时留空＝沿用旧 key）。不装 `openai` SDK，标准库 `urllib` 直发，少一层依赖和版本兼容问题。

内置常见服务预设（点一下自动填 base_url 与模型名，key 自己申请；免费额度以各家官网为准）：硅基流动 `api.siliconflow.cn/v1`、智谱 `open.bigmodel.cn/api/paas/v4`（glm-4-flash 长期免费）、DeepSeek、阿里百炼 `dashscope.aliyuncs.com/compatible-mode/v1`、Moonshot、ModelScope（每日 2000 次）、OpenRouter（`:free` 路由）、本地 Ollama `localhost:11434/v1`（数据不出网）。同类做法可参考 `songquanpeng/one-api`、`BerriAI/litellm`——它们也是把各家收敛到 OpenAI 协议，本项目只需单点直连所以没引网关。

报告提示词里带的是**统计口径 + 互动量 TOP60 样本**（平台/主体/情感/互动量/标题），要求模型按「总体结论 → 议题聚类 → 传播结构 → 风险评级 → 重点帖子 → 建议动作」输出，并在系统提示里禁止编造数据里没有的数字。生成走后台任务（30~120 秒），报告落 `data/reports/*.md`，页面内可看可下载。连通性测试与生成失败都会把上游返回的原文带出来（例如 `HTTP 401：{"error":...}`），不吞错误。

## 采集准确性：相关性闸门

搜索引擎会把"相关但不含词"的结果一起放出来。采集时默认开启闸门：标题或正文必须出现关键词本身或它的**核心词**（`开屏广告 → 开屏`、`摇一摇广告 → 摇一摇`，因为标题常写简称），否则丢弃并在日志里报数。实测「摇一摇广告」抓 15 条，闸门剔掉 7 条无关内容，入库 8 条；剔除量会写进采集历史的备注（`2026-08-25~2026-08-31 上限15 命中8/15`），可以回溯。

关键词云走 `hub/wordcloud.py`：无分词库依赖，n-gram + 停用词 + 长词优先，并**先抹掉「开屏广告」这类背景词**再统计（否则"开屏广""屏广告"这种碎片会把云占满）。点云里的词直接跳到明细页搜该词。

## 覆盖率与新鲜度（为什么要切片）

搜索入口都只放出「头部结果」：百度对一个 query 大约给 5~7 页，`s.weibo.com` 对一个大区间只给前几页。所以**一次查 3 个月，必然只拿到最热的几十条**，看起来就是「不够全、不够新」。

现在的做法是把大区间切成小窗口，同一个关键词查多次，从最近的窗口往回扫：

- 微博：**按天**切（`Weibo._days()`，最多 120 天），每天翻 10 页 —— 这也是 `dataabc/weibo-search` 的思路；再叠加容器接口的综合/实时两路补量。
- 百家号 / 微信公众号：**按 7 天**切（`article.week_slices()`，最多 26 段），每段翻 3 页百度结果，切片写进 `extra.slice` 便于回溯。
- 头条号 / 小红书：入口本身不支持时间参数，只能多翻页 + 本地按发布时间过滤，越早的内容召回越低。

采到多少、够不够新，直接看看板底部**「平台覆盖与新鲜度」**表：`有时间占比`低说明该入口不给发布时间（会被严格时间过滤挡掉），`覆盖天数 / 区间天数`低说明切片深度还不够，`最新发布`就是该平台数据的新鲜度上限。

## 已知边界

- 互动指标能拿多少完全取决于平台是否公开，**不做估算填充**：微信公众号、百家号网页侧根本不给数字（已用评论中台接口核实为 0）；头条号只有网页镜像口径的小数字；真正完整的赞/评/转/藏只有微博（已通）和小红书 / 抖音 / 快手（需扫码）。所以现在跨平台横向比「互动量」还不成立，只能比「帖子数」。
- 时间区间只有百度系（微信、百家号）和登录态微博是服务端精确过滤，其余靠解析卡片日期后本地过滤，越早的内容召回越低。
- 单账号高频抓取会触发验证码，`config.THROTTLE_SEC` 默认 1.2 秒；命中验证码时用 `--headful` 人工过一次，登录态会留在 profile 里。
- `data/` 下有登录态和 cookie，**不要提交到仓库**。
